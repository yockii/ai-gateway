    - Sustain 500 users for 3 minutes
    - Ramp down to 0

    - Simulate realistic user behavior
    - Mix of API calls: chat, models list, usage stats
    - Think time between requests (1-3 seconds)

    - Thresholds: P95 latency < 100ms for non-chat requests

    - Maximum QPS test
    - Start at 1000 QPS, ramp to 15000 QPS
    - Find breaking point
    - Record latency at each QPS level
    - Target: 10000+ QPS with <20ms P95

    - Use environment variables for API_URL and API_KEY
    - Implement setup() for authentication
    - Implement teardown() for cleanup
    - Record custom metrics (error rate, latency trend)

    - Include request headers (Authorization, Content-Type)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI runner → Docker registry | CI needs authenticated push access |
| CI runner → deployment target | CI needs deployment credentials |
| Load tester → API | Load tests should only run against test/staging |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-11 | Spoofing | CI/CD triggers | mitigate | Require branch protection, signed commits for production |
| T-04-12 | Tampering | Docker images | mitigate | Image scanning in build pipeline, signed images |
| T-04-13 | Information Disclosure | CI logs | mitigate | Secret redaction, never echo secrets, GitHub Actions secrets masking |
| T-04-14 | Denial of Service | Load tests | mitigate | Load tests only run on staging/localhost, never production |
| T-04-15 | Escalation | Deploy permissions | mitigate | Production deployment requires manual approval, separate environments |
</threat_model>

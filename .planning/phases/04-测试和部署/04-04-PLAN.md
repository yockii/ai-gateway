```yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: ai_gateway
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
  ai-gateway:
    build:
      context: .
      dockerfile: Dockerfile
    depends_on:
      postgres:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "wget", "--spider", "http://localhost:8080/health"]
```

  <action>
    Create blue-green deployment automation:

    **scripts/blue-green-deploy.sh:**
    - Accept environment (staging/production) and image tag as arguments
    - Determine current deployment color (blue/green)
    - Deploy new version to opposite color
    - Wait for health check (up to 30 attempts, 2s interval)
    - Run smoke tests against new deployment
    - Call switch-traffic.sh to switch traffic
    - Scale down old deployment
    - Exit with error on failure (manual rollback)

    **scripts/switch-traffic.sh:**
    - Accept target color (blue/green) as argument
    - Update nginx configuration to point to target
    - Reload nginx (nginx -s reload)
    - Verify new configuration is active
    - Rollback nginx config on failure

    **scripts/rollback.sh:**
    - Accept environment as argument
    - Identify current color
    - Switch traffic back to previous color
    - Verify rollback succeeded
    - Optionally: scale down failed deployment

    All scripts should:
    - Use set -euo pipefail
    - Log all actions with timestamps
    - Use descriptive variable names
    - Include usage messages
    - Validate arguments

    Add nginx service to docker-compose.prod.yml for blue-green.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| nginx → ai-gateway | nginx terminates TLS, forwards HTTP |
| docker host → containers | Container isolation limits access |
| deployment scripts → production | Requires proper authentication |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-16 | Spoofing | SSL/TLS | mitigate | Valid certificates from trusted CA, HSTS enabled |
| T-04-17 | Tampering | Docker images | mitigate | Use specific image tags in production, verify digests |
| T-04-18 | Information Disclosure | Logs | mitigate | Structured logging, sanitize secrets, log rotation |
| T-04-19 | Denial of Service | Resource limits | mitigate | Container resource limits, rate limiting, circuit breakers |
| T-04-20 | Escalation | Container escape | mitigate | Non-root containers, read-only filesystem, minimal base images |
| T-04-21 | Spoofing | Deployment access | mitigate | SSH key authentication, MFA, audit logging |
</threat_model>
